A build, narrated

Building the Ophtho Case Log

A veterinary ophthalmologist described a tool in plain English. This is what happened next — including the two bugs, the privacy finding that changed the design, and the parts where the description turned out to be the hard bit.

Chrome extension · ezyVet · local case log Written for people who do not code

01

The thing being built

Veterinary students on an ophthalmology rotation need to record what they saw: which patient, what the chief problem was, whether it was a new consult or a recheck, whether they scrubbed into a procedure. At the end of the rotation, that log goes to the service chief.

The tool is a panel that opens beside ezyVet — the electronic medical record the hospital already uses — with a spider chart showing the spread of cases across seven areas of ophthalmic interest, a button that reads the open patient's details off the page, and an export that prints to PDF.

Four questions, asked before any code

The description was detailed, and still underspecified in four places that each change what gets built. Rather than guess and rework, the answers came first.

QuestionAnswerWhy it changed the build
How should patients be identified? Patient name only — no medical record number Sets the ceiling on how identifiable the saved log can ever be
What do we inspect in ezyVet? A real patient record Determined how the inspection tool had to be written
Quizzes in version one? Deferred Kept version one shippable; the hook stayed in the code
Which export format? PDF report Removed the need for a spreadsheet path entirely
Why this matters

The planning conversation is the specification. Everything after it is a consequence. Someone who has never written code can do this part better than most programmers, because it is entirely about knowing the work — what a case record actually contains, what a service chief actually needs to see.

03

No toolchain, on purpose

Most software projects begin by installing a stack of build tools that convert the code you write into the code the computer runs. This one has none. The folder is the program: change a file, press reload in Chrome, see the change.

Nine small files, each with one job:

manifest.json          the ID card: name, permissions, what opens where
src/background.js      four lines — make the toolbar icon open the panel
src/panel/panel.html   both screens, dashboard and case form
src/panel/panel.css    styling, including dark mode
src/panel/panel.js     switching between screens, wiring the buttons
src/panel/store.js     saving and loading — the whole privacy surface
src/panel/taxonomy.js  the seven areas of interest, as plain data
src/panel/radar.js     the spider chart, drawn by hand
src/panel/extract.js   the only code that touches an ezyVet page
Why no chart library

Drawing a spider chart is a solved problem — there are libraries for it. But Chrome extensions are not allowed to fetch code from the internet while running, so a library would have to be copied into the folder: several hundred kilobytes of someone else's code to draw seven lines. The hand-written version is about ninety lines and reads top to bottom.

Why the vocabulary is its own file

The seven areas — orbit, adnexa, cornea, KCS, uvea, glaucoma, retina/neuro — live in one plain list. Adding an eighth later is one line. The chart, the form and the printed report all read from that list, so none of them needs touching.

04

First run

Chrome loads an unfinished extension straight from a folder — turn on Developer mode, press Load unpacked, pick the folder. It appeared first try, and a Load sample cases button filled it with eight invented patients so the layout could be judged with something in it.

One real defect: the word Glaucoma was clipped off the left edge of the chart. The drawing area had been sized to fit the chart, but the thing that sticks out furthest is the label — "Glaucoma 1" extends leftward from a point already close to the edge. The fix was a small circle inside a wide frame rather than a big circle in a tight one.

Why it was fixed with arithmetic

The fix was checked by calculating where all seven labels would land — the leftmost pixel of text now sits 34 pixels inside the frame, with room to spare for two-digit counts. Checking by eye would have confirmed only that it looks fine at today's numbers. Bugs that appear at case twelve are the expensive kind.

05

Reading the page without reading the record

For the extension to pull a patient's name off an ezyVet screen, it has to know where on that screen the name sits. Nobody knew — ezyVet's internal structure isn't published, and it had to be discovered from a live hospital system holding real client data.

The tool built for this returns the page's structure and not its contents. It reports where things are, with the actual values swapped for placeholders. A second pass masks everything: every letter becomes x, every digit becomes 9, so a line comes back as its shape alone. 

"Xxxxxx (XX)"                  → a name and a sex code
"Xxxxxx (Xxx) - Xxxxxxx"       → species, common name, breed
"9 xxxxx xxx"                  → an age

That is enough to write a parser and reveals nothing about the patient.

Why bother, when the record was open anyway

It is the same principle the finished extension runs on. The task needs structure, so the tool should be built to return structure — because designing for the narrower thing is more reliable than remembering to be careful with the wider one. Discipline that depends on remembering eventually fails.

What the page turned out to be

  • The web address is always just /. ezyVet is a single-page application, so the address can never say which patient is open — detection has to come from the page itself.
  • The open record's tab is #rtab7 and its patient panel is #patientSideBar7. That shared number links them, and it became the anchor the extension uses.
  • The panel's first line holds the name and sex together.
06

Two things worth finding before writing the code

Finding one

The label on the open record's tab reads 1204311 - "Fluffy" KUPRITZ (09-09-2026). That trailing surname belongs to the owner, not the animal. It is the most convenient-looking place to read a patient name from, and using it would have quietly carried client identity into every student's laptop.

Finding two

The day's appointment calendar sits in the same page. Every booking on it carries hidden identifiers for its client, its patient and its consult. An extractor written as "grab what's on the page" would harvest the entire day's caseload from a single button press.

Neither of these is a bug. Nothing was broken, and nothing would have looked wrong. They are visible only if you look at the page before writing the code that reads it — and they are the whole argument for the design that followed.

Three rules for the extractor

  1. It runs only when the button is pressed. The conventional way to build this is a script that loads on every ezyVet page and stays running. That would work identically from the student's side, and it would mean code sitting on every page all day, within reach of that calendar. Instead the code is sent into the page at the moment of the click, runs once, and is gone.
  2. It reads one element. The patient panel of the open record, and nothing else on the page.
  3. It returns five fields. Name, species, breed, sex, age. It is not a "read the page" function that gets filtered afterwards — it cannot return anything else.
07

Nine invented patients

Before the extractor was pointed at a real record, it was tested against nine made-up ones: abbreviated ages, an en dash instead of a hyphen, a missing breed, a two-word patient name, everything crammed onto one line.

All nine failed. The cause was two steps in the wrong order — the code tidied up spacing before splitting the panel's text into lines, and tidying collapses line breaks, so the whole panel fused into a single string. Swapping the two steps fixed all nine.

Why this is the most important paragraph here

That bug would have been nearly invisible on a live patient. The tool would have returned a name, missed the species, and looked exactly like ezyVet simply not displaying what we expected. Someone would have spent an afternoon inspecting the hospital system for a fault that was ours.

Invented patients found it in under a second, and they can be run again after any future change — including a change made by someone who has forgotten why the order mattered.

One of those tests checks something no human reviewer could reliably verify by reading: that the diagnostic report the extension can produce contains no characters other than x, X, 9 and punctuation. The privacy promise is enforced by a test, not by a comment.

08

The export, and a library that wasn't needed

The log has to reach a service chief as a document. Generating PDFs is normally a job for a specialised library — but Chrome already contains one. The export builds an ordinary printable page inside the extension and lets the browser's own print dialogue save it. Zero added dependencies.

Why this keeps coming up

Three times in this build the answer was to use something already present rather than add something new: the browser as the PDF engine, the browser's own storage as the database, hand-drawn shapes instead of a chart library. Every dependency is a thing that can break, needs updating, and has to be explained to whoever maintains this next.

09

Auditing the finished thing

A separate pass at the end, run against the code rather than against intentions. Each row is a check anyone can repeat with a search across the project — which matters, because the point is that you don't have to take anyone's word for it.

ClaimHow it was checkedResult
It cannot send data anywhere searched for every way code can make a network request none present
It loads nothing from the internet searched every web address in the source none
It does not run on pages by itself checked the manifest for always-on scripts none declared
It can only reach ezyVet read the permission list ezyVet only
Patient data never reaches the console searched every logging statement one, logging a Chrome error
Page text is never treated as instructions checked how every value reaches the screen as text, never markup
Storage holds only the agreed fields read the single function that builds a record 14 fields, all listed

What the audit could not fix

Three risks remain, and naming them is more useful than pretending they aren't there:

  • The free-text summary is the largest remaining leak, and it is human. Nothing stops a student typing an owner's name into it, and that text is printed in the report. A line under the field now warns that it will be printed. That is a nudge, not a guarantee.
  • The PDF is the one thing that leaves the machine, and it contains patient names and signalment by design. That flow is intended — but it deserves to be said out loud rather than left implicit.
  • Local storage is not encrypted. Anyone using that Chrome profile can read the log. On a shared hospital machine, students should use their own profile.

What transfers to the next build

The specification was the expertise

Nothing in this build required knowing how to program. It required knowing what a case record contains, that a procedure can accompany a new consult or a recheck or stand alone, and that a chief complaint and a secondary problem are different things. That knowledge is not recoverable from a vague request, and no amount of technical skill substitutes for it.

The constraints did more work than the features

"Extract only what's needed, and flag anything that risks capturing more than intended" is one sentence in the brief. It produced the on-demand design, the five-field limit, the masked inspection tool, and the audit — and it caught the owner surname before a single student ever ran this.

Ask to see the plan before the code

The file layout, the extraction approach and the form flow were all described and agreed before anything was written. Two layout changes came out of that conversation. Both would have been rework if the code had gone first.

Testing against invented data isn't ceremony

Nine fictional patients found a bug in a second that a real patient would have disguised as somebody else's fault. If you take one habit from this document, take that one.

The parts of this that were hard were the parts a clinician is trained for: deciding what a case record must contain, noticing that a surname on a tab label belongs to a person who never consented to being in a student's logbook. The typing was the easy half.
